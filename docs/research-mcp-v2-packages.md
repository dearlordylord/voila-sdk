# Research: migrating to the MCP TypeScript SDK v2 packages

Date: 2026-08-12

## Conclusion

Migrating `@firfi/voila-mcp` from `@modelcontextprotocol/sdk` v1 to the split v2 packages is viable and is the right way to remove **Voila's direct Zod API use and direct `zod` dependency**. It will **not produce a Zod-free dependency graph**: the current `@modelcontextprotocol/server`, `@modelcontextprotocol/client`, and `@modelcontextprotocol/core` packages all declare Zod as a runtime dependency in their official manifests ([server manifest](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/packages/server/package.json), [client manifest](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/packages/client/package.json), [core manifest](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/packages/core/package.json)).

For this repository, the recommended target is:

- Production dependencies: `@modelcontextprotocol/server` and `@modelcontextprotocol/node`.
- No production dependency on `@modelcontextprotocol/client`: the current source implements a server and its tests do not import the MCP client. Add the client as a development dependency only if tests are later rewritten to exercise the server through an in-memory or stdio MCP client.
- No direct dependency on `@modelcontextprotocol/core`: it is the public package for raw protocol Zod `*Schema` constants, and the current code only needs types re-exported from the server package ([official package split](https://ts.sdk.modelcontextprotocol.io/v2/migration/upgrade-to-v2#packaging-runtime)).
- Replace MCP-facing Zod schemas with the Effect schemas that already exist in `packages/voila-mcp/src/operation-schemas.ts`, converted to JSON Schema 2020-12 and wrapped with `fromJsonSchema<T>()` from `@modelcontextprotocol/server` ([official schema-library guide](https://ts.sdk.modelcontextprotocol.io/v2/advanced/schema-libraries)).

## Package status and maturity

As of 2026-08-12, `@modelcontextprotocol/server` and `@modelcontextprotocol/client` are both at `2.0.0`, require Node.js 20 or newer, and ship ESM and CommonJS exports ([server manifest](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/packages/server/package.json), [client manifest](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/packages/client/package.json), [v2 runtime guidance](https://ts.sdk.modelcontextprotocol.io/v2/migration/upgrade-to-v2#packaging-runtime)). This repository already requires Node 20 and is ESM, so those requirements are not blockers.

The official repository identifies v2 as the stable line implementing the 2026-07-28 protocol revision, while also warning that the new API is still settling; v1 continues receiving bug and security fixes during its stated maintenance window ([official SDK README](https://github.com/modelcontextprotocol/typescript-sdk#readme)). That makes migration reasonable now, but it should be treated as a real major-version migration with full server transport and protocol tests, not as import-only churn.

The v2 client and server remain wire-compatible with v1-era peers through protocol negotiation. The new 2026-07-28 behavior is negotiated explicitly, while ordinary initialization retains compatibility with legacy protocol revisions ([official protocol-revision migration guide](https://ts.sdk.modelcontextprotocol.io/v2/migration/support-2026-07-28)). API objects and nominal types are not interchangeable between installed v1 and v2 packages, so a staged migration must keep the two implementations separated at a process or wire boundary ([official staged-migration guidance](https://ts.sdk.modelcontextprotocol.io/v2/migration/upgrade-to-v2#migrating-in-stages-large-codebases)).

For the first migration, keep the current protocol era deliberately: a directly connected `McpServer`/`Server` and `StdioServerTransport` continue speaking the 2025-era protocol by default. The separate `createMcpHandler` (HTTP) and `serveStdio` entry points opt a server into serving the 2026-07-28 era ([official 2026-07-28 serving guide](https://ts.sdk.modelcontextprotocol.io/v2/migration/support-2026-07-28#serving-the-2026-07-28-revision)). Adopting those entry points should be a later, explicit protocol-design change rather than an incidental part of removing direct Zod use.

## What “remove Zod” can mean

V2 makes tool, prompt, and output schema registration validator-library-neutral through `StandardSchemaWithJSON`. A compatible schema must expose both `~standard.validate`, used for calls, and `~standard.jsonSchema`, used to advertise the schema in `tools/list` ([official schema-library guide](https://ts.sdk.modelcontextprotocol.io/v2/advanced/schema-libraries)). Zod v4 and ArkType work directly; Valibot needs its JSON Schema adapter; raw JSON Schema works through `fromJsonSchema()` ([official schema-library guide](https://ts.sdk.modelcontextprotocol.io/v2/advanced/schema-libraries)). Raw Zod field-shape objects remain only as deprecated overloads in v2, so new code should register a complete schema object ([official server-registration migration section](https://ts.sdk.modelcontextprotocol.io/v2/migration/upgrade-to-v2#standard-schema-objects-raw-shapes-deprecated)).

Effect's `Schema.standardSchemaV1()` supplies Standard Schema validation, but the installed Effect implementation does not attach the additional `~standard.jsonSchema` member required by MCP. Therefore, passing it directly is not a supported `StandardSchemaWithJSON` bridge. The safe bridge is:

1. Keep the existing Effect `Schema.Struct(...)` values as the source of truth.
2. Generate JSON Schema 2020-12 with Effect's `JSONSchema.make(schema, { target: "jsonSchema2020-12" })` ([Effect 3.21.4 source documentation](https://github.com/Effect-TS/effect/blob/effect%403.21.4/packages/effect/src/JSONSchema.ts)).
3. Wrap the document with `fromJsonSchema<Input>(document)` so MCP infers the handler input type and validates incoming calls with its runtime-selected JSON Schema validator ([official `fromJsonSchema` example](https://ts.sdk.modelcontextprotocol.io/v2/advanced/schema-libraries#start-from-json-schema-you-already-have)).

On Node, the v2 SDK selects AJV for `fromJsonSchema` by default; users do not have to install AJV for that default path. A custom validator must be passed as the second argument to `fromJsonSchema`, because the server's `jsonSchemaValidator` option governs elicitation form responses rather than schemas already wrapped by `fromJsonSchema` ([official validator guidance](https://ts.sdk.modelcontextprotocol.io/v2/advanced/schema-libraries#swap-the-json-schema-validator)).

This bridge removes the duplicated MCP-only schema vocabulary now present in `mcp-server.ts` and makes the already-defined Effect operation schemas the single boundary contract. It also aligns with this repository's “Schema as Source of Truth” rule. A small generic helper should centralize the conversion so every registration uses the same JSON Schema target and typing.

`runVoilaOperation` should continue parsing the received argument through the Effect schema even after MCP validates it. The MCP wrapper protects the protocol boundary and publishes `tools/list`; the existing Effect parse remains the authoritative application-boundary parse and typed error path. This matters for transforms: the current MCP-only Zod strings use `.trim()`, which accepts padded input and returns a trimmed value, whereas the Effect `Schema.trimmed()` refinements reject strings that are not already trimmed. Migrating to the Effect-generated contract intentionally chooses the latter behavior and needs a regression test.

| Hand-written `makeTransportAdapter` compatibility wrapper | Connect the Node transport directly, subject to typecheck | V2's transport contract is unchanged and v1-era hand-written adapters should need only import updates; the migration guide also says old double casts/workarounds should be removed because v2 types satisfy the contracts directly ([official transport compatibility](https://ts.sdk.modelcontextprotocol.io/v2/migration/upgrade-to-v2#unchanged-apis), [official packaging cautions](https://ts.sdk.modelcontextprotocol.io/v2/migration/upgrade-to-v2#packaging-runtime)). |
| Raw Zod shapes in `inputSchema` | Complete `fromJsonSchema<Input>(...)` schema objects | Raw shapes are deprecated; use complete Standard Schema-with-JSON objects ([official schema guidance](https://ts.sdk.modelcontextprotocol.io/v2/advanced/schema-libraries)). |

The current code already uses `registerTool(name, config, handler)`, so it avoids one of the largest v2 breaks: the old variadic `.tool()`, `.prompt()`, and `.resource()` methods were removed ([official registration migration](https://ts.sdk.modelcontextprotocol.io/v2/migration/upgrade-to-v2#server-registration-api)). Its handlers also do not use the old `extra` object, so the `extra.*` to `ctx.mcpReq.*` / `ctx.http.*` migration does not affect the existing tool implementations ([official context mapping](https://ts.sdk.modelcontextprotocol.io/v2/migration/upgrade-to-v2#low-level-protocol-handler-context-ctx)).

## Proposed implementation sequence

1. Run the official codemod in dry-run mode at `packages/voila-mcp`, then inspect its import and manifest proposal. The upstream quick path is `npx @modelcontextprotocol/codemod@latest v1-to-v2 .`; in this pnpm repository the equivalent should be run through `pnpm dlx`, with `--dry-run` first. The codemod updates imports and the nearest manifest but intentionally leaves manual-review markers for transformations it cannot prove safe ([official codemod guide](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/packages/codemod/README.md), [official migration quick path](https://ts.sdk.modelcontextprotocol.io/v2/migration/upgrade-to-v2#tl-dr-quick-path)).
2. Add `@modelcontextprotocol/server` and `@modelcontextprotocol/node` to `packages/voila-mcp`; retain v1 temporarily only while sources still import it. Do not add `@modelcontextprotocol/client` unless a concrete client use is introduced.
3. Introduce one MCP-schema adapter that accepts a context-free Effect Schema, emits JSON Schema 2020-12, and returns typed `fromJsonSchema`. Avoid casts, consistent with the repository's cast ban.
4. Replace every duplicated Zod input definition in `mcp-server.ts` with the corresponding existing schema from `operation-schemas.ts`. Replace `{}` for no-input tools with the wrapped `EmptyOperationInputSchema`; v2 treats a registration with no `inputSchema` as a context-only callback, which would silently change the handler parameter meaning ([official no-input warning](https://ts.sdk.modelcontextprotocol.io/v2/migration/upgrade-to-v2#server-registration-api)).
5. Move stdio and HTTP imports. Use `NodeStreamableHTTPServerTransport` and test whether the current transport adapter can be deleted; retain a wrapper only if it provides behavior beyond the old type workaround.
6. Remove `@modelcontextprotocol/sdk`, the direct `zod` declaration, and all direct Zod imports only after `rg '@modelcontextprotocol/sdk|from "zod"'` is clean in the package. The official staged order is add v2, migrate sources, then remove v1 ([official staged-migration guidance](https://ts.sdk.modelcontextprotocol.io/v2/migration/upgrade-to-v2#migrating-in-stages-large-codebases)).
7. Update tests to assert `tools/list` JSON Schemas and invalid `tools/call` inputs, because conversion correctness and runtime validation are the main new seam. Preserve the existing independent Streamable HTTP session tests. If adding `@modelcontextprotocol/client` for integration tests, use `Client` from its root and stdio transport from `@modelcontextprotocol/client/stdio` ([official client guide](https://ts.sdk.modelcontextprotocol.io/v2/get-started/first-client)).
8. Run `pnpm check-all`. No live Voila smoke test is needed for this protocol-layer-only migration unless operation behavior or live endpoints are changed.

## Risks to test explicitly

- **Effect-to-JSON-Schema drift:** confirm minimum/maximum, integer, literal, optional, record, array length, regex, and unknown-value behavior survive conversion and are enforced by MCP's validator. Snapshot or structurally assert every advertised input schema.
- **Empty-input callback semantics:** always register an explicit object schema; omitting it changes the single callback argument to the server context ([official registration migration](https://ts.sdk.modelcontextprotocol.io/v2/migration/upgrade-to-v2#server-registration-api)).
- **HTTP transport integration:** the Node transport class and package change even though its options and request surface remain. Exercise initialize, session routing, GET/DELETE behavior, JSON-response mode, and session cleanup ([official transport compatibility](https://ts.sdk.modelcontextprotocol.io/v2/migration/upgrade-to-v2#unchanged-apis)).
- **Node adapter peer warning:** `@modelcontextprotocol/node` depends on `@hono/node-server`, whose own `hono` peer can cause a harmless unmet-peer warning even though the Node adapter does not require the Hono framework. Do not add Hono solely to silence that warning without first confirming the workspace's peer-dependency policy ([official packaging guidance](https://ts.sdk.modelcontextprotocol.io/v2/migration/upgrade-to-v2#packaging-runtime)).
- **Behavioral test expectations:** v2 changes some list aggregation, absent-capability behavior, lazy validator compilation, and JSON Schema posture. Review the upstream behavioral changes rather than assuming v1 snapshots remain exact ([official behavioral-change section](https://ts.sdk.modelcontextprotocol.io/v2/migration/upgrade-to-v2#behavioral-changes)).
- **Mixed v1/v2 objects:** never pass server, client, transport, or error objects between the two package generations during a staged migration; only their negotiated wire protocol is a safe boundary ([official staged-migration guidance](https://ts.sdk.modelcontextprotocol.io/v2/migration/upgrade-to-v2#migrating-in-stages-large-codebases)).
- **Upstream settling period:** pin compatible v2 ranges deliberately, keep lockfile review in scope, and run the complete quality gate on upgrades while the v2 API settles ([official SDK README](https://github.com/modelcontextprotocol/typescript-sdk#readme)).

## Recommendation

Proceed with a focused v2 server migration. Frame its dependency outcome precisely: it removes Voila's direct dependency on and authored use of Zod, consolidates MCP input contracts onto Effect Schema, and adopts the supported split SDK packages. It does not remove Zod transitively because the official v2 implementation still uses it internally.
